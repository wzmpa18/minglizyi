## 三、内容引擎修复明细（本次技术攻坚）

### 3.1 JSON解析四重修复（parseAIJson，wechatContentEngine.js）

glm-4.5-flash 输出的 JSON 有三类高频故障，V8 报错特征与修复方案：

| 故障形态 | V8报错特征 | 修复 |
|----------|-----------|------|
| 正文里未转义英文双引号 | Expected ',' or '}' after property value | ①紧邻CJK的引号转义为 \u0022 |
| 已知key后漏写冒号（key换行后顶格跟值） | Expected ':' after property name ... column 1 | ②`"key"\s*(?=["[{])` 补冒号 |
| 全角冒号写在key引号外 | Expected ':' ... column 4 | ③`"key"：` → `"key":` |
| **全角冒号嵌进key字符串内部**（`"takeaway："值"`） | Expected ':' ... column 1（报错点在下一行`}`） | ④`"key："` → `"key": "` |

**关键经验**：修复④必须在修复①之前执行——全角冒号在CJK字符类内，修复①会先把 `："` 误判为内容引号转义掉，导致④的模式消失（实测踩坑）。

**落地验证**：3 个真实故障 dump 文件（服务器 `data/ai_parse_fail_*.json`）全部用新修复链解析成功，takeaway 完整恢复。

解析失败时原始输出自动落盘，后续再遇新故障模式可直接取证加固。

### 3.2 标记式目标字数扩写（buildExpandPrompt + mergeExpand）

**背景**：glm-4.5-flash 首稿系统性偏短（实测 702/839/937/996 字），且扩写走 JSON 重输出时解析失败率高。

**方案**：
- 扩写改**纯文本标记格式**（`【开场】`/`【小节N】` 逐段补写），响应不涉及 JSON，从根上规避解析失败
- **目标字数感知**：按缺口计算补写量（目标 1850 字，每部分 1 段约 N 字），修复"1019→2735"过冲超 2500 字上限作废的问题
- mergeExpand 按标记合并段落，过滤标题提示行，无标记响应自动跳过（原稿不受损）

**实测**：#26 数字减法 702→1561 字；#28 玄奘 839→2143 字——全部落入达标区间。
