## 二、每次开始工作前：强制阅读和核对

1. 先阅读工作区根目录 `AGENTS.md`、本制度、权威交接报告和 `PROJECT_MASTER_LEDGER.md`；若任务落在具体子项目，还必须阅读该目录的 `AGENTS.md`。
2. 核实当前工作区绝对路径、Git 分支与未提交改动；对照报告中的版本、服务器、应用商店和未完成事项，确认哪些信息是历史证据、哪些需要实时复核。
3. 不得把旧截图、历史记录、上传草稿、接口 200 或“账号获得资格”说成当前审核通过或已上架。无法实时验证时必须标为“未核实”，注明最后证据日期。
4. 若权威报告缺失、E 盘不可用或镜像哈希不一致，先恢复/修复报告副本并记录原因；不得另开一份报告绕过。

## 三、每次完成工作前：必须写入可接手记录

每项任务结束前，必须在权威报告末尾加入一条带日期的明确增量，至少说明：

- 用户目标、完成范围和明确未做事项；
- 修改/新增/删除的文件绝对路径，以及关键行为变化；
- 测试、构建、真机/网页/接口/平台验证的实际结果和证据位置；未做的验证必须明说；
- 发布版本、渠道、状态及平台回执；准备好、上传、提交审核、审核通过、正式发布必须分别记录；
- 风险、未完成事项、下一位开发者第一步；
- 本次清理了哪些临时文件/旧包，保留了哪些仍被使用或用于审计的文件；
- 工作区报告与 E 盘镜像的 SHA-256 结果。

必须写清“本次改了什么、证据在哪里、还差什么”。不得只写“已更新”“持续完善”“后续继续跟进”，不得用承诺代替事实。资料不足时也要记录已查到的证据和阻塞点，不能伪造完成状态。

## 四、每次收工的工作区清理：强制执行

1. 结束前盘点本次产生的临时脚本、日志、截图、缓存、解包目录、构建中间件、失败产物、重复文档和旧安装包。
2. 删除已完成任务不再需要的临时文件、重复报告、失败/过时 APK 或安装包，以及一次性脚本；不要把清理工作留给下一位开发者。
3. 仅保留源码、用户原始资料、密钥/生产配置、正式交付物、仍在提审或回滚所需的安装包、有效测试证据和有追溯价值的历史记录。无法判断用途时先核对引用和哈希；不确定的用户资料/密钥/源文件不得删除。
4. D/E 盘归档与生产数据不因“清理工作区”而默认可删。删除 E 盘用户源资料、密钥、生产配置、正式材料或正在使用的发布包前，必须有明确授权和备份验证；清理范围限于已确认的项目临时物。
5. 删除后复核源码/正式交付物仍在、最新候选包和需要保留的旧测试 AAB 未误删；在交接增量中列明清理结果。不得以磁盘空间为由删除唯一备份或有效审核证据。

## 五、同步和完成门槛

1. 完成本地权威报告后，将同一文件同步到 E 盘交接目录及上述兼容镜像位置。
2. 对权威文件和 E 盘镜像计算 SHA-256；哈希必须一致。不能同步时必须把任务标为未完成并写出错误，不能说“已交付”。
3. 检查所有交接路径都能打开、最新增量存在、报告未被截断；运行适用的格式/链接/代码校验。
4. 只有报告已更新、工作区已清理、镜像哈希一致、验证与未完成项如实记录后，才可把本次开发任务标为完成。

## 七、2026-10-18负责人追加硬性制度：提交、清场与两代留存

本节由项目负责人本次明确授权，覆盖前文宽泛的“有追溯价值即可保留旧包”等表述；不得再凭开发者个人判断无限留存版本。

1. 每次交付前，本次有效源码、配置、必要维护脚本、文档和确定的删除记录必须审查、验证、提交并推送指定分支。必须读回提交号、上游差异及git status；禁止把仅本地修改、stash、补丁文件、整目录备份当作已提交。密钥、账号会话、生产数据、安装包、缓存禁止为凑“干净”而提交。
2. 收尾要求git status --porcelain为空且HEAD与上游一致。继承的未提交改动必须逐项查明用途、归属、差异及处理结果：有效且已验证者提交；确认失败/无用者清除；来源或数据价值未核实者记为具体阻塞并继续处置，不能掩盖后宣称完成。禁止无审查git add -A、git clean -fdx或reset --hard。
3. 每次结束必须清理临时脚本、日志、缓存、解包、失败构建、重复报告、旧安装包和已失效的一次性指令。真正仍在使用的维护脚本必须纳入源码、说明用途，不能以“以后可能有用”堆积临时文件。清理后实际检查路径不存在、文件数和磁盘可用空间；只发命令不等于已清理。
4. 每个产品/确实不同的发布渠道只允许两个物理版本集合：一份当前新版和一份紧邻且已验证可回滚的旧版。源码日常维护只保留一个活动工作区，历史依靠Git，不以多个整目录拷贝充当版本管理。Google与国内差异包不能相互替代；同一版本的APK/AAB及必要签名清单归属同一集合，禁止同版本多处冗余包。
5. 新版须通过适用的构建、包名/版本/签名/哈希、关键功能、部署/商店状态核对，达到本次声明的“正常可用”条件，才轮换旧备份。轮换顺序：核实新版→核实当前版可作回滚→删除更老备份、失败候选及对应无用产物→仅保留新版+一个旧版→更新版本/路径/用途/哈希和验证证据。未通过或未验证的新版不能冒充稳定版；被拒/失败且无继续修复价值的候选及时清除。
6. 此规则同样覆盖C/D/E物理归档与任务副本，不是每个盘再保留两代。唯一权威交接报告及强制规定的固定镜像不属于“安装包重复备份”，镜像仍必须同步校验。保留小体积真实审核证据、法定记录和密钥，不得借清理删除唯一生产数据。
7. 交接必须写明：本次提交与推送证据、遗留未提交项清单、当前/唯一回滚版、具体已删除路径和字节数、残留检查、命令、镜像SHA-256。提交、清理、两代轮换或同步任一未落实，状态必须写未完成/阻塞；不得写“全部完成”。
8. 历史97副本遗留变更尚未审结，本次不因新增制度就宣称已达标；禁止盲目提交缓存/审核凭证或删除待审语料。下一位开发必须先处理该明确历史债务，不得再复制出新源码目录延续问题。

### 每次必须执行并记录的命令（在国学活动仓目录）

    git diff --check
    git status --short
    git diff --stat
    git ls-files --others --exclude-standard
    git add -- <逐个审查过的具体文件路径>
    git commit -m "<具体改动及验证>"
    git push
    git rev-parse HEAD
    git rev-list --left-right --count HEAD...@{upstream}
    git status --porcelain

最后两项必须分别为0 0及空输出；记录“失败/权限拦截/没有上游”等真实结果，不得绕过。文档/镜像需要入仓者在提交前更新同步，提交后只读核验，避免提交后又改交接造成新的脏工作区。

物理清理必须先核对绝对路径和目录联接，必须使用唯一交接报告最新清理增量所指向的单一CMD及当次重新盘点的精确清单；第50节等旧增量的命令仅为历史证据，不得直接执行。路径已不存在时应从可执行CMD中移除对应过时指令；旧清理清单不能自动扩展为磁盘根目录/全盘删除。删除后复查正式包和必要证据仍在，并计算实际释放量。
